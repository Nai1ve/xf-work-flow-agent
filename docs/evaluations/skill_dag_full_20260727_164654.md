## 根因分析

### 1. 请假 schema 枚举映射没有闭环

语义模型正确保留了 `病假`、`年假`、`身体不舒服` 等自然语言标签，workflow schema 也返回了真实的 `leave_type_options` 和 `reason_options`。但 leave form compute 节点没有完成最后的候选映射，导致有效请求被阻塞为 `missing_required_info` 或 `invalid_leave_form`。

代表 case：

- `beta_wf_0203`：需要在 schema 候选中选择与 `病假`、`身体不舒服` 对应的真实 value。
- `beta_wf_0223`：`年假` 需要与 schema 标签 `年休假` 做语义选择，不能恢复为 Python 固定映射。

诊断信息也存在缺口：47 个 `missing_required_info` task 均没有输出具体缺失字段，无法区分真实缺槽与 schema 翻译失败。

### 2. Read 步骤会耗尽 Write 预算

完全取消未来 write 预留解决了之前的证据读取死锁，但冗余 fallback read 现在可能耗尽全部 simulator step。

`beta_mr_0215` 只要求 `本周五`，Agent 却依次查询了 5 月 11、12、13、15 日四次 `room.list`。找到有效会议室后，已经没有步骤执行 `booking.create`。

预算应改为动态策略：

- 证据未确定前，不为所有未来 write 硬预留。
- 用户请求范围已经得到有效候选后，立即停止 fallback 扩展。
- 进入确定写分支后，只为当前紧邻的 write 节点保留 1 步。

### 3. 多时段日期字段兼容不完整

`beta_mr_0041` 的模型输出使用 `date_desc=周三` 和 `date_desc=周四`。当前 normalizer 支持 `date_ref`、`day_text` 和 `day`，但不支持 `date_desc`，导致两个时段都被解析为 5 月 6 日。

第一次预订成功，第二段因为工具参数完全相同而触发 `duplicate_skill_invocation`。最终结果又用 `booking_create_failed` 覆盖了已经产生的部分成功。

### 4. 最近工位会议室投影使用了错误标识

`beta_mr_0230` 和 `beta_mr_0245` 已成功预订最近会议室。工具返回了 UUID 形式的 `officeId`，结果投影却将其替换成建筑标签 `A1`。

外部结果契约要求保留工具返回的真实 `office_id`。建筑信息应单独投影为 `building`，不能覆盖 office 标识。

### 5. 项目空结果映射不能稳定收敛

19 个 task 以 `ambiguous_project` 结束。例如 `beta_wf_0059` 依次查询：

1. `品牌市场产品发布会`
2. `品牌市场产品发布`
3. `品牌市场`
4. `市场推广`

所有查询均为空。LLM 生成的 Top 3 查询词没有覆盖能够命中真实项目的核心表达。当前机制仍是在生成额外查询文本，而不是基于真实项目候选做排序。重试耗尽后，project 节点保持 pending，直到 scheduler 统一清理。

### 6. 仍存在重复 capability

两个基础 case 生成了等价的重复任务：

- `beta_mr_0013`：两个 `meeting.book`
- `beta_wf_0018`：两个 `workflow.leave_submit`

会议室 case 中，第一个任务已经成功预订，第二个任务仍继续查询并影响最终聚合结果。TaskGraph normalizer 需要按 `capability + canonical slots` 去重，同时保留用户明确要求的不同重复写操作。

### 7. Failure edge 仍依赖 scheduler 清理

上一轮 compute 解锁 read 后直接退出的问题已经不再是主要 stall 来源。当前 stall 主要发生在候选已耗尽、节点无法再生成 read action，但 failure edge 没有主动进入终态的场景。

项目空结果、会议室无候选和人员搜索耗尽后，应直接进入带精确 reason 的 blocked 终态。`scheduler_stalled` 应只代表调度不变量被破坏，不能成为正常业务失败的收尾机制。

## 修复优先级

1. 增加基于 schema 候选的请假类型、原因和审批人映射 compute handler；按输入 hash 缓存，不增加固定业务映射。
2. 多时段日期支持 `date_desc`，并在 repeat write 中保留部分成功结果。
3. 增加动态紧邻 write 预算，并在硬约束范围已经命中后停止会议室 fallback。
4. booking result 恢复真实工具 `officeId`，建筑信息单独输出。
5. SkillRun 初始化前去除语义等价的重复任务。
6. 将项目、会议室和人员候选耗尽路径改成显式 terminal failure edge。
7. 项目空结果映射必须经过真实工具候选验证，不能直接接受自由生成的关键词。
8. 对 timeout、`502`、`503` 的语义请求增加一次受控退避重试，或者在比较业务逻辑前单独重跑语义失败 case。

## 结论

本轮存在部分结构性改善：净恢复 4 个通过 case，多轮和复杂跨域通过率上升，ReadPlan 基本全部成功执行。但它还不能作为稳定业务基线，因为 API 失败显著增加，同时 schema 映射、预算分配、日期标准化、任务去重和结果投影仍存在确定性退化。

下一轮应先为上述确定性问题增加定向回归测试，再进行全量评测。报告中需要继续将 API 失败与业务失败分开统计，避免外部服务波动掩盖 DAG 本身的变化。
